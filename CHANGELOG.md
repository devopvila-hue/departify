# Changelog

## [Unreleased]

### Added

- ROSA adoption.
- Golden Image foundation with Docker backend image, compose file, Railway config, Netlify portal config, Supabase CLI config, centralized typed configuration, and environment variable contract.
- Provisioning Engine foundation with public contracts, pipeline phase definitions, explicit state model, validation primitives, adapter ports, and unit tests.
- Organization Domain foundation with canonical aggregate root, value objects, lifecycle policy, domain events, pure invariants, and unit tests.
- Application Layer foundation with commands, queries, handlers, DTOs, mappers, application services, ports, validation, and unit tests.
- Persistence Contracts foundation with repository contracts, unit of work, transactions, specifications, pagination, filters, optimistic locking, provider-neutral errors, and unit tests.
- Supabase Persistence Adapter with official Supabase client configuration, repository implementations, snapshot mappers, local migration, UnitOfWork adapter, unit tests, and local integration tests.
- Platform Composition foundation with the first real organization provisioning flow persisted through Supabase local, plus repeatable end-to-end coverage.
- Agent Runtime foundation with provider-independent registry, lifecycle state policy, permissions, internal messaging contracts, scheduling contracts, runtime events, validation, and unit tests.
- Agent Domain foundation with canonical aggregate root, value objects, lifecycle policy, domain events, pure invariants, and unit tests for digital employees.
- Executive Director foundation with intents, routing, planning, decision model, coordination contracts, internal events, validation, and unit tests.
- LLM Router foundation with provider-neutral contracts, capabilities, abstract model catalog, routing policies, requests, responses, validation, and unit tests.
- OpenAI LLM Provider Adapter foundation with official SDK isolation, typed configuration through `packages/config`, request/response mappers, chat/completion/structured-output/tool-calling/streaming support, unit tests, and live integration test wiring.
- Memory Engine foundation with memory records, context assembly, sessions, retention policies, retrieval contracts, lifecycle rules, internal events, validation, and unit tests.
- Knowledge Engine foundation with documents, chunks, sources, collections, scopes, abstract indexing, retrieval contracts, ranking policies, lifecycle rules, internal events, validation, and unit tests.
- LLM Router composition with official `bootstrapLlmRouter` entry point, internal `ProviderRegistry`, provider-agnostic observability (`RouterLogger`, `RouterMetrics`, `InMemoryRouterMetrics`, `createNoopObservability`, `createConsoleObservability`, `createInMemoryObservability`), routing policies `capability_first` and `balanced` plus the existing strategies, configuration-driven default provider and strategy via `packages/config` (`LLM_DEFAULT_PROVIDER`, `LLM_ROUTING_STRATEGY`), `LlmRouter` facade exposing `chat`, `complete`, `embed`, and `stream`, and a registry bridge in `packages/llm-provider-openai` (`registerOpenAIProvider`).
- Multi-provider foundation with `packages/llm-provider-google` (Google Vertex AI / Gemini), `packages/llm-provider-minimax` (OpenAI-compatible HTTP), `packages/llm-provider-bridge` (the single multi-provider composition entry point), typed configuration via `packages/config` for `GOOGLE_VERTEX_*`, `GOOGLE_APPLICATION_CREDENTIALS`, `MINIMAX_*` plus a typed enum for `LLM_DEFAULT_PROVIDER`, an expanded `LLM_DEFAULT_PROVIDER` enum (`openai`, `google_vertex`, `minimax`), and unit + integration tests for every new provider.
- Tool Runtime foundation with `packages/tool-runtime`. Domain model (`Tool`, `ToolDefinition`, `ToolExecutionRequest`, `ToolExecutionResult`, `ToolExecutionContext`, `ToolCapability`, `ToolMetadata`, scopes), explicit `ToolRegistry` (`register`, `unregister`, `get`, `has`, `list`, `validate`), six-phase execution pipeline (`validate → authorize → prepare → execute → observe → complete`), permissions, isolation, timeout, cancellation and limits policies, provider-agnostic observability (`ToolLogger`, `ToolMetrics`, `InMemoryToolMetrics`, `NoopTool*`), and the internal event taxonomy (`tool.registered`, `tool.requested`, `tool.started`, `tool.completed`, `tool.failed`, `tool.cancelled`). Real execution is disabled in Sprint 20; the package ships contracts, registry, pipeline shape and policies only. Zero external dependencies: no SDKs, no `process.env`, no HTTP, no Fastify/Supabase/Docker.
- Agent ↔ Tool Runtime integration with `packages/agent-tool-bridge`. New `AgentToolPort` interface (the only authorised contract between Agent Runtime and Tool Runtime) and `AgentToolRuntimeAdapter` implementation that translates `AgentToolAction` into `ToolExecutionRequest` and back, derives Tool scopes from Agent permissions via `DefaultAgentPermissionScopeResolver`, and never modifies either runtime. Ships the `system.time` demonstration Tool (pure local computation: `timestamp`, `timezone`, `iso8601`) and 11 tests covering success, missing tool, unknown agent, denied authorization, executor failure, and cancellation.
- Core Tool Catalog with `packages/tool-catalog`. Five Tool definitions: `system.uuid` (uuid + version via Node crypto), `organization.get` (uses `packages/organization-domain` snapshot contract through a host-supplied resolver), `memory.search` (uses `MemoryRetrievalPort` from `packages/memory-engine` with typed selection policy, no embeddings), `knowledge.search` (uses `KnowledgeRetrievalPort` from `packages/knowledge-engine` with typed selection + ranking policy, no vector search), `system.health` (typed snapshot of runtime + tool runtime + router + provider registry). Single composition point `registerAllCoreTools(registry, context)` registered via the existing Tool Runtime pipeline; no new runtimes, bridges, packages, IA, HTTP, or external SDKs. 26 unit and integration tests including Agent Runtime → AgentToolBridge → Tool Runtime end-to-end paths for `system.uuid` and `organization.get`.
- Executive Orchestration Pipeline with `packages/executive-orchestrator`. The Executive Director is now wired into the runtime flow as the deterministic decision engine. The orchestrator defines `OrchestratorIntent` types (`health_check`, `organization_summary`, `generate_identifier`), an `ExecutiveDecisionMapper` (the only component authorised to translate `ExecutiveDecision` into `AgentToolAction`), and an `ExecutiveOrchestrator` facade that drives the full pipeline `OrchestratorIntent → ExecutiveDirector → DecisionMapper → AgentToolBridge → Tool Runtime → Core Tool Catalog`. The pipeline preserves the intentId → decisionId → actionId correlation chain inside the typed `OrchestrationResult` envelope. 18 unit and integration tests including end-to-end runs that invoke `system.health`, `organization.get` and `system.uuid` through the orchestrator and assert successful, rejected and failure paths. No IA, no LLM Router, no HTTP, no SDKs. Existing public contracts of Executive Director, AgentToolBridge, Agent Runtime, Tool Runtime and Tool Catalog are untouched.
- Department Model Foundation in `packages/departments`. Sprint 24 introduces the **external product unit** — a Department is a composition of references to existing components, never a duplicate of their state. The package ships the Department aggregate (identity, configuration, lifecycle states `draft` → `active` → `paused` → `archived`, metrics, event taxonomy), the `DepartmentService` composition entry point (`create`, `addEmployee`, `removeEmployee`, `associateTool`, `associateMemorySession`, `associateKnowledgeCollection`, `activate`, `pause`, `archive`), and the canonical `Comercial` demo with four Digital Employees (`agent_sales_director`, `agent_lead_qualifier`, `agent_outreach_specialist`, `agent_proposal_writer`) and pre-associated Tools, Knowledge Collections, Memory Sessions and connected applications. The Department aggregates never execute logic; they only reference Agent Runtime, Executive Director, Tool Runtime, Tool Catalog, Memory Engine and Knowledge Engine. 25 unit and integration tests including end-to-end wiring with Agent Runtime, Tool Runtime and Core Tool Catalog. No IA, no LLM Router, no HTTP, no SDKs. Existing public contracts of all other packages are untouched. **External vs internal naming.** The Department is the visible unit of the product; the Digital Employee is the internal execution unit.
- Business Provisioning in Sprint 25. Adds `DepartmentTemplate`, `DepartmentTemplateCatalog`, `DepartmentTemplateBuilder` and the canonical `Comercial` template inside `packages/departments` (the catalog is the single authorised source for initial Departments — hardcoded Departments are forbidden outside the catalog). Extends `packages/provisioning-engine` with the `instantiate_business` pipeline step and a typed `BusinessProvisioningResult` envelope (organization + departments + employees + resources). Adds `BusinessProvisioningService` inside `packages/platform-composition` that drives `Organization → DepartmentTemplateCatalog → DepartmentService → Department → Digital Employees + Tools/Knowledge/Memory` after a successful Organization provisioning. The flow is idempotent and reports failures through typed `ProvisioningIssue` entries (`BUSINESS_TEMPLATE_MISSING`, `BUSINESS_DEPARTMENT_FAILED`). 42 new tests (32 in `packages/departments`, 10 in `packages/platform-composition`) covering template validation, Comercial composition, idempotency, controlled failure and the full Organization → Comercial department flow. No IA, no LLM Router, no HTTP, no SDKs, no CRUD. Existing public contracts of every other package are untouched.
